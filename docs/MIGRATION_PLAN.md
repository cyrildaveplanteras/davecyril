# GoldenHope Electron — MySQL → PostgreSQL Migration Plan

## 1. Executive Summary

GoldenHope is an offline-capable Electron desktop application (vanilla JS renderer, Node main
process, `mysql2` over a local XAMPP MySQL server). This plan migrates the primary database from
MySQL to a locally-run PostgreSQL 16 instance while preserving all features, business rules,
financial calculations, and the exact result-row shapes the renderer expects.

## 3. Target Architecture (PostgreSQL)

```
Renderer (src/)  ── IPC (window.api.*) ──►  Main process (main.js)
                                                    │  execute(sql, params)   [MySQL-style ? params, converted to $n]
                                                    ▼
                                          PostgreSQL service (src/js/database.js)
                                                    │  pg Pool (connection pooling, retry, error mapping)
                                                    ▼
                                          Local PostgreSQL 16 (port 5432, offline)
```

- Renderer NEVER talks SQL or carries credentials. Same security boundary as today.
- Mixed-case column names preserved exactly (`"Id"`, `"AFNo"`, `"RemittanceNo"`, ...) so the
  renderer's PascalCase/snake_case access patterns keep working without frontend changes.
- DATE/TIMESTAMP returned as strings (matches `dateStrings:true` behavior).
- `?` positional params written in source; the driver converts to PostgreSQL `$1..$n`.

## 4. PostgreSQL Schema

All 31 MySQL tables re-created in PostgreSQL with identical names and column names/types:

- `AUTO_INCREMENT` → `GENERATED BY DEFAULT AS IDENTITY` (preserves migrated IDs).
- `TINYINT(1)` → `SMALLINT` (keeps `1/0` numeric semantics the renderer uses truthiness-style).
- `DATETIME`/`TIMESTAMP` → `TIMESTAMP` (no tz); `ON UPDATE CURRENT_TIMESTAMP` → app-side or
  `MODIFIED` trigger-less (updated explicitly in UPDATE statements).
- `MEDIUMTEXT`/`TEXT` → `TEXT`; `DECIMAL(10,2)` → `NUMERIC(10,2)`.
- `ENGINE=InnoDB`, backticks, `CHARACTER SET` dropped.
- Indexes: same as MySQL plus indexes for search/filter/join hot paths (af_no, full_name,
  municipality_id, barangay_id, member_status, DateDeposit, RemittanceId, etc.).
- FKs: identical to MySQL (`ON DELETE CASCADE/SET NULL`), financial rows never cascade-deleted.

### Mapping notes
- Table `ActivityLogs` (PascalCase) — kept as-is (quoted identifier).
- `ref_*` and `psgc_*` tables are already lowercase — kept lowercase.

## 5. Migration Procedure

1. **Back up MySQL** (mysqldump) to `GoldenHopeBackups/` (never overwrite).
2. **Export MySQL data** via a new Node script using `mysql2` + `exceljs`.
3. **Create PG schema** from the definitive schema module (`src/js/pg-schema.js`).
4. **Import PSGC** from `PSGC-2Q-2026-Publication-Datafile.xlsx` into `ref_*` (PG upsert).
5. **Import members, remittances, details, commissions, deductions, users, settings,
   notifications, branches, personnel, lock_logs, login_attempts, membership_audit_log,
   data_change_log, death_cases, hda_deductions, pending_remittances.**
   - Resolve AF-No ↔ MemberId orphan links; backfill `MemberId` in `remittance_details`.
   - Recompute derived `remittances.TotalDeposit` from NetDeposit sums.
6. **Validate relationships** (FK integrity, orphan checks) and **reconcile totals** vs old DB.
7. **Migration report** (Records Found / Migrated / Matched / Corrected / Failed / Manual Review).

## 6. Business Rules Preserved (spot checks)

- First MSC → 0% commission; 2nd MSC onward → 5% (`MSC_COMMISSION_RATE`).
- ₱120 Sales Coordinator commission per qualifying MF (250/350) remittance.
- Remittance posting = single atomic transaction (validate → MF → MSC → commission → records →
  funds → statements → balances → COMMIT / ROLLBACK).
- Monthly/system lock via `lock_logs` state machine (Scheduled → Active → Expired/Cancelled).
- Activity Log records only LOGIN / LOGOUT.
- Member balances computed from verified transactions (no divergent copies).

## 7. Components to Rewrite

- `src/js/database.js` — new PostgreSQL service (`pg` Pool): `?`→`$n`, `insertId` via `RETURNING`,
  date-as-string type parsers, `getConnection()`/`beginTransaction()`/`commit()`/`rollback()`,
  MySQL error-code → friendly messages, connection retry/wait, `ensureDatabase`.
- `main.js` — all SQL rewritten to PostgreSQL dialect (identifiers quoted, `DATE_FORMAT`→`to_char`,
  `DATE_ADD`→`+ INTERVAL`, `CURDATE`→`CURRENT_DATE`, `ON DUPLICATE KEY`→`ON CONFLICT`,
  `LAST_INSERT_ID`→`RETURNING`, `GET_LOCK`→advisory locks, etc.); backup/restore via `pg_dump`/
  `psql`/`pg_restore`.
- `scripts/init-db.js`, `scripts/psgc-importer.js`, `scripts/reconcile.js`, `scripts/fix-*.js`,
  `scripts/test-*.js`, `migrate-afno.js`, `fix-*.js` — ported to PG.
- `src/js/auto-xampp.js` → `src/js/auto-postgres.js` — detects/starts local PostgreSQL instance
  (portable bundled instance or system service); removed MySQL/Apache auto-start.
- `.env` / `.env.example` — PG connection variables (`PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`,
  `PGDATABASE`, plus `DB_*` kept for migration tooling).

## 8. Testing & Acceptance

- Automated: business-rules unit tests, DB consistency checks, migration report, reconciliation,
  financial scenarios (1st/2nd/3rd MSC, failed remittance, reversal).
- Manual/automated app run: login, members, PSGC address, remittance, commissions, SOA, reports,
  exports, notifications, settings, month lock, backup/restore.
- Final report against the master prompt's acceptance checklist.

## 9. Risks & Mitigations

| Risk | Mitigation |
|------|-----------|
| Renderer key-casing breakage | Keep exact column names; migration test asserts row keys. |
| Silent financial drift | Reconciliation report compares every financial total old vs new. |
| Partial migration | Every import runs in a transaction; report lists failed rows for manual review. |
| PostgreSQL not installed on user machine | Bundle portable PG binaries; auto-detect + auto-init + auto-start. |
| Timezone/date drift | `timestamp` without tz; connection `timezone=Asia/Manila`; strings returned. |
